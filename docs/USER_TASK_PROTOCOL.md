# 用户任务测试协议

## 目的

验证系统是否帮助用户更快、更少误判地找到“今天真的值得继续核验并投递”的岗位。它不是满意度调查，也不衡量 Offer 概率。

## 参与者

- 最低 3 人，目标 5 人；
- 当前处于 2027 届实习或校招阶段；
- 每人使用自己的简历事实和明确城市偏好；
- 不公开参与者简历、姓名或完整岗位表。

## 任务

> 在 15 分钟内找出 5 个上海优先、2027 届可投、本人愿意投，并能说明官方状态依据的具体岗位。

## 对照方式

采用同一候选集、同一用户的两种流程，顺序在参与者间交替：

1. 原始表格＋浏览器；
2. 校招岗位决策台。

两轮使用等量但不同的候选子集，避免记忆答案。测试前不向参与者透露系统排序逻辑。

## 记录指标

| 指标 | 定义 |
| --- | --- |
| `time_to_5_seconds` | 得到 5 个满足任务定义岗位的时间；15 分钟未完成则记 900 秒并记录数量 |
| `valid_candidates_found` | 时间内最终保留且经主持人复核满足硬条件的数量 |
| `officially_confirmed_count` | 有当前具体官方岗位页或明确官方证据的数量 |
| `false_eligible_count` | 被用户判为可投、但存在明确硬条件不符的数量 |
| `candidates_inspected` | 用户打开或详细查看的候选数量 |
| `manual_corrections` | 用户纠正分类、字段、画像事实或系统结论的次数 |
| `critical_confusions` | 使用户无法继续或产生错误投递决定的交互问题 |

## 主指标

`15 分钟内找到的、官网有依据且满足硬条件的可投岗位数`。

`time_to_5` 仅在两种流程都完成 5 个时比较。小样本只报告每人的原始结果与中位数，不做统计显著性声称。

## 主持人核验

- Campaign 不计作具体岗位；
- `NOT_FOUND / BLOCKED / UNKNOWN` 不计作官网确认；
- 页面有申请入口只表示页面仍开放，不表示存在实际 headcount；
- 明确城市、届次、学历或招聘类型不符计为 false eligible；
- 信息未写清计 Unknown，不强行判 Pass。

## 迭代规则

测试完成后，只选择影响人数最多或导致明确错误决策的一个 Bad Case 进入下一轮；修复后重跑契约集，并邀请至少 1 名参与者复测关键任务。

## 尚未执行声明

本协议是待执行材料。项目目前没有真实用户测试结果，任何简历或演示中都不能写“节省 X% 时间”或“用户推荐准确率 X%”。记录模板见 `evaluation/task-test-template.csv`。

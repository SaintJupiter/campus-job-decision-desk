# 简历与面试表述

## 项目名称

**多源校招岗位核验与投递决策系统｜个人产品 / 数据项目**

## 当前可直接使用的简历三条

- 针对国内校招聚合表中 Campaign、岗位族与多城市混杂的问题，设计并实现 `DataSource–ImportBatch–RawRecord–Opportunity–FieldClaim` 可追溯数据模型；在 7,919 条私有记录的聚合评测中形成 7,890 个机会实体与 79,648 条字段 Claim，机会来源覆盖率 100%。
- 将可投性、简历证据匹配与信息可信度拆为 Eligibility / Evidence Fit / Trust 三轴；实现官网域、共享 ATS 租户、岗位 ID、状态五态与 14 天新鲜度门禁，避免 404 被误判关闭、Campaign 证据泄漏和过期结论继续导出。
- 完成 FastAPI + React 全栈产品、只读合成 Demo 与可复现评测器；25/25 条安全边界契约和 8/8 条合成回归样本通过，本地岗位池/工作区/详情端点中位响应 28.46 / 52.92 / 3.35 ms。

## 暂时不要写

- “推荐准确率 100%”；
- “节省 80% 选岗时间”；
- “提升面试率 / Offer 率”；
- “覆盖全网岗位”；
- “AI 自动判断岗位真实性”。

## 完成用户测试后才可替换的结果句

仅当真实记录完成且结果成立时，写成：

> 在 N 名 2027 届学生的同任务对照中，15 分钟内找到的“硬条件满足且官网有依据”岗位中位数由 A 提升至 B，明确误资格由 C 降至 D；基于最大 Bad Case 完成一次迭代。

不要把小样本写成统计显著，也不要将后续面试结果归因于系统。

## 30 秒项目介绍

“Offerbiu 和 OfferComing 主要解决岗位发现与投递管理，FreeHire 解决全球 ATS 聚合。我遇到的问题更上游：国内付费秋招表常把招聘项目、多个岗位和多个城市放在一行，不同来源还会冲突。我的系统先保留不可变原始数据和字段级来源，区分 Campaign 与具体 Posting，再把能不能投、简历有什么证据、信息能不能信分开，并只让有当前官网依据的具体岗位进入可信导出。它不是另一个 AI 匹配分 Demo，而是一套可审计的决策流程。”

## 面试高频追问

### 为什么不用大模型直接打分？

因为可投性包含确定性硬条件，缺失不能当满足；大模型只适合做带原文 Span 的结构化抽取和解释，不应成为最终资格裁决者。

### 为什么不直接用 Offerbiu？

可以用它做下游投递跟踪。本项目从用户已有多份表开始，解决 Campaign/Posting、字段级来源冲突、官网证据和来源独立性，输出结果可以继续交给现有工具。

### 去重怎么验证？

官方 ID 与规范化具体 URL 才允许精确复用；公司、标题、城市和届次只生成候选，低置信结果必须人工确认。不同官方 ID 或公司不自动合并。

### Codex 做了什么，你做了什么？

可以坦率说明使用 Codex 加速编码、测试和审查；个人贡献应聚焦问题定义、竞品边界、数据模型、状态机取舍、验收标准、失败案例判断和最终结果负责。演示时应能独立解释每条不变量为什么存在。

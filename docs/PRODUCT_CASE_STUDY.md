# 产品案例：多源校招岗位核验与投递决策系统

## 一句话

把用户已有的多份校招表，转换成一份“能不能投、值不值得投、信息能不能信”相互分离且可追溯的具体岗位清单。

## 问题不是缺一个岗位库

Offerbiu、OfferComing 已覆盖岗位发现、AI 选岗和投递管理；FreeHire 已展示全球 ATS 聚合、统一 Schema、搜索与求职工作台的完整工程思路。真正未被当前场景解决的问题发生在更上游：用户购买的国内校招表把 Campaign、职位族、城市集合和截止说法混在一行，不同供应商还可能相互复制或冲突。

本地数据证明这个问题不是为了做项目而虚构：7,909 条岗位型记录中，53.1% 疑似一行多岗位或宽泛岗位族，39.1% 多城市，77.2% 没有明确截止日期。

## 产品判断

没有先解决岗位粒度和信息可信度，就不应该给出精确匹配分。因此系统采用以下顺序：

```text
用户自带来源
→ 不可变 RawRecord
→ Campaign / Posting
→ 字段 Claim 与来源冲突
→ 具体官网身份与状态核验
→ Eligibility / Evidence Fit / Trust
→ 可信短名单
```

## 关键取舍

### 不自动拆 Campaign

“产品/算法/运营 × 上海/杭州/深圳”不能自动生成 9 个岗位。首版只隔离 Campaign，再由用户绑定实际官方 Posting，避免把笛卡尔积当事实。

### 不让 LLM 决定可投性

城市、届次、学历、类型和开放状态由确定性三值规则判断。未写清就是 Unknown，不能用模型常识补齐。

### 不用一个总分

Eligibility、Evidence Fit、Trust 分开呈现。用户可以看到“硬条件通过，但经历证据弱”或“经历匹配，但信息陈旧”，而不是面对无法解释的 82%。

### 不全量自动抓官网

两周内实现所有 Moka、飞书、微信和企业动态站既不现实，也会把项目变成脆弱爬虫。系统只对用户选择的 Top-K 做人工辅助核验，并把 blocked/unknown 当合法结果。

## 最有含金量的实现

1. Claim-level provenance：同一字段保留每个来源、时间、解析器、权威等级和证据；
2. Campaign / Posting 状态机：重分类时旧身份、关系、Claim 适用性和决策全部失效；
3. 官网信任锚：域名、公共后缀、聚合平台、共享 ATS 租户和官方岗位 ID 共同约束；
4. 决策快照版本：画像、偏好、Claim、官网域、岗位身份或 14 天窗口变化后自动失效；
5. 服务端可信导出：不信任前端显示，导出时再次执行全部门禁；
6. 隐私双运行形态：本地私有工作区与只读合成演示完全分开。

## 结果

- 25 / 25 条安全边界契约通过；
- 8 / 8 条开发者合成启发式样本通过；
- 7,919 条私有 RawRecord、7,890 个机会、79,648 条 Claim 完成聚合结构评测；
- 机会来源覆盖率 100%，原始记录物化覆盖率 99.87%；
- 本地端点中位延迟 3.35–52.92 ms；
- 完成响应式 Web UI、合成只读 Demo、评测报告、隐私门禁与自动化测试。

这些是工程与数据结构结果，不是求职转化结果。

## 失败案例推动的迭代

独立边界审查与回归测试曾发现并修复：任意 URL 冒充官网、共享 ATS 租户串线、Campaign 证据泄漏到 Posting、陈旧决策继续展示、跨目录静态文件读取、同一来源伪装成多个独立来源、未来快照压过当前事实等问题。项目的可信度主要来自这些边界被测试固化，而不是功能数量。

## 下一步

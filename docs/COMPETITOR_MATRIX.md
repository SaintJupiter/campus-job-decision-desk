# 竞品功能矩阵与差异化边界

> 更新日期：2026-08-10。本项目只比较各产品官网或官方仓库公开展示的能力；“未见公开证据”不等于对方内部一定没有。

## 先说结论

本项目不是 Offerbiu、OfferComing 或 FreeHire 的替代品：

- 如果目标是“海量找岗位 → 改简历 → 自动填表 → 跟踪面试”，应直接用它们；
- 如果输入是“用户已经买了多份中国校招表，每份都会更新，但字段、粒度、时效和官网状态互相冲突”，本项目解决的是这个更上游的信息可信化问题。

## 四个产品的正确定位

| 产品 | 更准确的定位 | 可快速借鉴的地方 | 不直接复刻的地方 |
| --- | --- | --- | --- |
| [Offerbiu](https://www.offerbiu.com/) | 国内求职工作流产品：岗位、简历版本、JD/AI 匹配、面试和投递进度 | 岗位卡信息优先级、状态跟踪、人工确认 | 完整投递 Kanban、简历优化、自动填表 |
| [OfferComing](https://offercoming.cn/) | 中国校招岗位聚合、AI 选岗与投递工作流 | 届次、批次、城市、企业性质、免笔试、截止时间和投递阶段等本土化工作流 | 自建另一个海量岗位库、会员、题库和泛化资讯体系 |
| [FreeHire](https://github.com/strelov1/freehire) | 全球官方 ATS 岗位目录与开源求职工作台 | source adapter、canonical schema、stable dedup、faceted search、API、事件审计 | 全球抓取基础设施、邮箱、内推、完整 CV builder/agent |
| 校招岗位决策台 | 用户自带多份校招来源的可追溯核验与投递决策层 | 国内校招筛选语言、基础投递阶段和事件化数据模型 | 不做海量发现、自动网申和完整面试 CRM |

FreeHire 官方 README 当前公开展示了官方 ATS 导入、统一 Schema、稳定去重、多维搜索、公开 API、CV/JD 评分、AI fit、投递板和邮件工作流等能力。这证明“再做一个通用 AI 求职助手”不足以构成差异化。

## “做到了多少”应如何表达

不宜用一个模糊的“完成度 80%”混合两种不同产品。可以按两个口径表达：

1. **按通用求职平台口径：约 45%–55%的功能面。** 有岗位池、国内校招筛选、证据画像、匹配、可信投递阶段和导出，但没有海量全网发现、简历改写、自动填表、邮箱和完整面试 CRM。这是主动取舍，不是遗漏。
2. **按“多源校招情报可信决策层”口径：核心工程闭环已完成。** 已实现来源导入/远程同步、不可变快照、差异、粒度隔离、字段 Claim、保守去重、官网核验、三轴结论、短名单门禁和安全导出。尚未完成的是外部 3 人任务测试与真实投递结果，因此不宣称提升面试率。

## 可在面试中使用的差异化回答

> Offerbiu 和 OfferComing 更适合找岗位与管理投递，FreeHire 更像全球官方 ATS 岗位目录。我没有重做这些已有能力。我的真实问题是，手里同时有多个付费校招表和每日更新的飞书视图，同一岗位的城市、届次、截止时间和状态会冲突，而且宽泛招聘项目不能直接和简历匹配。所以我做了一个用户自带数据源的可信决策层：全量快照、字段级来源、Campaign/Posting 分层、Top-K 官网核验，再把“能不能投、值不值得投、信息能不能信”分开。结果可以导出到任意下游投递工具，而不是取代它们。

## 边界与待验证项

- Offerbiu 很新且外部用户评价少，它是交互参考，不应包装成“人尽皆知的成熟行业基准”。
- FreeHire 的开源工程面很广，但不能因此推断它对中国 2027 校招的届次、批次和国内 ATS 覆盖已经充分。
- 本项目的飞书连接使用官方 API；普通 `/base/...` 链接若跳转登录，必须配置有权限的 access token/应用凭证，不会伪装成“粘贴任意网址都能抓”。
- 两周内的客观成果是数据与决策边界可复现，不是录用率提升。
